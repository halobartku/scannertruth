# Radar regression pack: 17 real Solana vulnerabilities, fixed and unfixed

This directory is corpus 2 of [scannertruth](https://github.com/halobartku/scannertruth) packaged
so that one command answers, for every rule change in Radar: does the rule mapped to a
vulnerability class still fire at the fix site of the vulnerable code, and is it silent on the
fixed code. It exists because Auditware/radar#34 had to repair detections that #33 lost, and
that is exactly the check a corpus of fixed-versus-unfixed pairs is for.

Every case is a real exploited or disclosed vulnerability with its upstream fix commit. Each
`cases/<id>/` holds the file the fix touched, twice: `insecure/` at the parent commit, `secure/`
at the fix commit, each with a minimal `Cargo.toml` so Radar accepts it as a crate. Provenance
(repository, fix commit, parent commit, public write-up) is in `expected.json`. The source files
are unmodified excerpts and remain under their upstream repositories' licences.

## Run

    ./run.sh

Needs `radar` on `PATH` (or `RADAR=/path/to/radar ./run.sh`) and Python 3, nothing else. It
stages every variant as `_staged/<id>.<variant>/pkg/`, runs `radar scan -p <staged> -f none -o
results/<id>.<variant>/radar.json` on each of the 34, keeps `stdout.log` beside each result, then
runs `python check.py`. About a minute per variant on our host.

To score results you already have: `python check.py --results <dir>` with the same
`<id>.<variant>/radar.json` layout.

## Verdicts

`check.py` is a thin wrapper around `score2.py`, the file that produced our published results
table. It is copied here verbatim, not re-implemented. One verdict per case:

| verdict | meaning |
|---|---|
| `detected` | a mapped rule fires within 3 lines of a line the fix changed, on the vulnerable variant, and not on the fixed one |
| `unlocated` | a mapped rule fires in the right file but not at the fix site, or fires on the fixed variant as well |
| `missed` | no mapped rule fires on the vulnerable variant |
| `no-rule` | the mapping names no Radar rule for this class; nothing to regress here yet |
| `not-run` | no `radar.json` and no `Scanned N file` line in `stdout.log`, so there is no evidence either way |

`fires_on_fixed` is the count of all findings on the fixed variant, mapped or not. It is an upper
bound on noise, not a false-positive count: a finding on fixed code can be a real defect the
fix did not address. We report it that way in our own results and ask that it be read that way here.

## The mapping is yours to correct

`mapping.json` is the class-to-rule mapping we pre-registered before measuring Radar, derived
from Radar's own rule names. Eight of the seventeen classes have no Radar rule mapped and score
`no-rule`. If a rule of yours does cover one of those classes, or a mapped rule is the wrong one,
say so in Auditware/radar#32 and we publish the corrected mapping as a new row beside the old.
`expected.json` lists, per case, the mapped rules, the fix-site lines the scorer uses and the
verdict we measured at the revision named in `reference_revision`.

## What this pack does not do

It does not measure rate of noise on already-correct teaching code; that is the other corpus. It
holds no unpublished cases. It is generated by `tools/regression_pack.py` in the repository above
and a test there fails if this copy drifts from a fresh build.
